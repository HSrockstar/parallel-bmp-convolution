# 2026-11-28 测评标准对齐自检

> 依据：老师 2026-11-28 公告（5 条测评标准 + 去年四核总时间前三名）。
> 目的：核对本项目原有的计时/构建/基准口径是否还能用于成绩测评；按新标准重测四核总时间。
> 结论先行：**旧口径的 8.6/8.7 ms（`-O3 -march=native`、5 次取最优）不能作为新标准下的成绩**。

> **2026-11-28 12:51 后续更新（当前代码）**：运行时检测的 AVX2 手写内核已并入主代码，
> plain `gcc -O2` 即可启用，不需要 pragma。当前首测：不绑核 Pthread 12.041 ms / OpenMP 12.271 ms；
> `taskset -c 0,2,4,6` 五次中位约 8.9 / 8.4 ms；教师验卷仍为 MSE=0.00、相似度 100.00%。
> 本文 §4、§7 的 23–27 ms 和 pragma 9.1 ms 是标量版本的历史数据，保留用于口径对照，
> **不代表当前代码**。原始记录见 `作业/结果/O2首测_20261128_125154_3598875/`。

## 1. 结论

| 口径 | Pthread | OpenMP | 取较快版本 | 相对去年第一（0.059117 s） |
|------|---------|--------|-----------|---------------------------|
| plain `gcc -O2`，4 线程，不绑核，首次运行 | 23.3–26.6 ms | 22.8–26.8 ms | **约 23–27 ms（0.023–0.027 s）** | 快 2.2–2.6× |
| plain `gcc -O2`，4 线程，`taskset -c 0,2,4,6`（4 物理 P 核），首次运行 | 19.1–19.3 ms | 18.9–19.2 ms | **约 19 ms（0.019 s）** | 快约 3.1× |
| 旧文档写法 `taskset -c 0-3`（实为 2 物理 P 核 + HT） | 32.2–32.8 ms | 32.0–32.3 ms | 约 32.5 ms | 快约 1.8× |
| 历史 `-O3 -march=native`，P 核，5 次取最优 | 7.13 ms | 7.08 ms | — | 仅优化分析口径，**不可用于新标准成绩** |

- **最可能的官方值**：老师若用“最朴素的 O2 + 4 线程、不绑核、首次运行”，约 **0.023–0.027 s**；若统一指令绑 4 个物理 P 核，约 **0.019 s**。
- 去年第一 0.059117 s，本方案在新标准下仍有 **2.2–3.1×** 优势。
- 最大不确定项不是代码，而是老师“统一编译运行指令”是否包含 `taskset` 以及绑哪几个 CPU。建议向老师确认；本文两种都留了数据。

## 3. 已做的对齐修改

### 3.1 代码

- `作业/代码/conv_pthread.c`、`conv_omp.c`
  - `t_all0` 移到 `main` 第一句，严格对应“程序首（第一次输入前）”。
  - `malloc/calloc/mmap` 增加显式类型转换，兼容 `g++ -O2`（防止老师统一指令用 g++ 时编译失败）。
  - OpenMP 未显式传线程数且未设 `OMP_NUM_THREADS` 时默认 4 线程；显式参数/环境变量仍优先。
- 计时终点不变：`close(out_fd)` 之后、`dump_kernel`/`dump_matrix`/`printf` 之前。
  - 即：输入打开/读头 + mmap + 输出文件创建/预分配 + 4 线程卷积（含输出映射写入）+ join + close 计入；
  - 卷积核/矩阵 txt 导出、控制台打印、munmap 不计入。

### 3.2 构建

- `作业/代码/Makefile` 新增：
  - `make official` → `gcc -O2 -pthread conv_pthread.c`、`gcc -O2 -fopenmp conv_omp.c`
  - `make official-run` → 调用 `run_official.sh`
- 历史 `-O3` 目标保留，仅用于优化日志/报告的算法分析，不再作为成绩口径。

### 3.3 运行

- 新增 `作业/代码/run_official.sh`：
  - 固定输入 `timg.bmp`、固定输出 `作业/结果/测评口径/official_output.bmp`；
  - 4 线程（Pthread/OpenMP 默认均为 4）；
  - 每个配置只跑第一次并抓 `Total time`；
  - 同时跑不绑核与 `taskset -c 0,2,4,6` 两组；
  - 每次跑完立刻过教师验卷器（`环境验证/test` 存在时）。

## 4. 实测数据

### 4.1 环境

| 项 | 值 |
|----|----|
| CPU | Intel Core i9-13900K，24 核 32 线程（8 P 核 + 16 E 核） |
| OS / kernel | Ubuntu 22.04，Linux 6.8.0-138-generic |
| 编译器 | 系统默认 `gcc` 10.5.0；另测 `gcc-11` 11.4.0、`g++` 11.4.0 |
| 输入 | `timg.bmp` 4096×2304×24bpp，约 27 MB；实测时页缓存已全量命中（`fincore` 27M/6913 页） |
| 输出 | 固定路径，每次运行前删除，模拟首次测评 |
| 负载 | loadavg ≈ 1.4–2.1（共享机，偶发外部负载；P 核绑核组最稳定） |
| 计时 | `clock_gettime(CLOCK_MONOTONIC)` / `omp_get_wtime()`，取程序打印 `Total time` |

### 4.2 五轮重复（plain `gcc -O2`，默认 4 线程，首次 + 中位数）

| 配置 | 首次 | 最小 | 中位数 | 最大 |
|------|------|------|--------|------|
| Pthread，不绑核 | 23.312 ms | 23.312 | 25.269 | 26.572 |
| OpenMP，不绑核 | 22.793 ms | 22.793 | 24.488 | 25.143 |
| Pthread，`taskset -c 0,2,4,6` | 19.149 ms | 19.028 | 19.085 | 19.149 |
| OpenMP，`taskset -c 0,2,4,6` | 18.995 ms | 18.930 | 18.995 | 19.107 |
| Pthread，`taskset -c 0-3` | 32.481 ms | 32.167 | 32.481 | 32.784 |
| OpenMP，`taskset -c 0-3` | 32.126 ms | 32.007 | 32.126 | 32.314 |

> 不绑核组波动明显（约 22.8–26.6 ms），原因是 4 个线程可能被调度到 E 核或发生迁移；
> 绑 4 个物理 P 核后非常稳定（18.9–19.2 ms）。老师若用“最朴素”的不绑核指令，单次首测可能落在 23–27 ms。

### 4.3 官方脚本单次首测（另一个时间窗）

| 配置 | Total time | Wall time (full) |
|------|-----------|------------------|
| Pthread，不绑核 | 25.690 ms | 27.861 ms |
| OpenMP，不绑核 | 26.773 ms | 28.114 ms |
| Pthread，P 核 `0,2,4,6` | 19.282 ms | 20.549 ms |
| OpenMP，P 核 `0,2,4,6` | 19.189 ms | 20.324 ms |

> 与 4.2 的差异属于共享机运行窗噪声（同一二进制、同一命令，首测在 22.8–26.8 ms 间浮动）。
> **绑核数据才是可复现的“真四核”值**；不绑核数据用于回答“老师最朴素指令”的可能结果。

### 4.4 编译器/指令变体（不绑核，首次）

| 编译器/链接 | Pthread | OpenMP |
|-------------|---------|--------|
| `gcc` 10.5 `-O2 -pthread` / `-O2 -fopenmp` | 23.312 ms | 22.793 ms |
| `gcc-11` 11.4 `-O2` | 25.369 ms | 24.108 ms |
| `g++` 11.4 `-O2` | 24.358 ms | 24.384 ms |

> 源码已加 cast，`g++ -O2` 也能编译；如老师统一指令用 g++，时间与 gcc 同量级。
> Pthread 版在 Ubuntu 22.04（glibc ≥ 2.34）下即使不写 `-lpthread` 也能链接；OpenMP 必须 `-fopenmp`。

### 4.5 冷输入页缓存的影响

| 条件 | Pthread P 核 | OpenMP P 核 |
|------|--------------|-------------|
| 输入已缓存（常规） | 19.1–19.3 ms | 18.9–19.2 ms |
| `posix_fadvise(DONTNEED)` 清空输入缓存后首跑 | 20.624 ms | 20.871 ms |

> 28 MB 输入的冷缓存代价约 +1.5–2 ms；老师连续测评多个同学时，从第二个起输入通常已热。
> 若要求严格统一，建议测评前先 `cat timg.bmp > /dev/null` 预热，或统一记录冷/热状态。

## 6. 口径细节与风险（建议向老师确认）

1. **“输出最终结果前”到底指什么？**
   本项目把“输出 BMP 写完（close）后、txt/控制台输出前”作为终点。这样计时**包含输出 BMP 的写入**（mmap 与卷积融合），只排除 txt 导出和打印，属于偏保守的口径，不会少算工作量。
   若老师要求“写 BMP 之前”就停表，需要改成“先算到内存缓冲、再单独写文件”，时间会略低；当前实现无法把 mmap 写与卷积拆开。
2. **`taskset` 是否是统一指令的一部分？**
   这是最大变数：不绑核 23–27 ms，绑 4 个物理 P 核 19 ms，绑 `0-3`（2 物理核 + HT）32 ms。三者都远快于去年第一，但数字不同。建议直接问老师统一指令是否含 `taskset`、绑哪几个 CPU。
3. **“第一次测评”是第一次跑该程序，还是第一次跑该配置？**
   本文按“每个配置第一次运行”记录，且每次先删除输出文件。若老师复用已存在的输出文件，`ftruncate/fallocate` 的块分配状态可能略有差异，实测在噪声内。
4. **输入页缓存冷/热**：冷输入 +1.5–2 ms；建议统一预热或统一冷启动。
5. **`Wall time (full)` 与 `Total time`**：前者多含 txt 导出 + munmap，约 +1.2–2.2 ms。老师按程序内 `Total time` 记录时用后者；若外部 `/usr/bin/time` 计时则接近前者。
6. **历史 8.6/8.7 ms 不能混用**：那是 `-O3 -march=native -funroll-loops -ffp-contract=fast` + 5 次取最优的优化分析口径；新标准下 plain `-O2` 关闭了自动向量化/FMA，热循环变回标量，时间约 19–27 ms，属预期。

## 7. 可选：plain -O2 下的源码级向量化（未并入主代码）

### 7.1 发现

plain `gcc -O2`（GCC 10/11）默认不开启 `-ftree-vectorize`，热循环（hpass/vpass）是标量。
在源文件顶部加一行：

```c
#pragma GCC optimize("tree-vectorize")
```

仍然用 `gcc -O2` 编译，GCC 会对热循环生成 16 字节 SSE2 向量（`-fopt-info-vec` 可见
“loop vectorized using 16 byte vectors”），无需 `-O3`/`-march=native`。

### 7.2 实测（timg.bmp，4 线程，首次 / 5 次中位数）

| 配置 | 标量 plain `-O2` | 加 pragma 后 plain `-O2` |
|------|------------------|--------------------------|
| 不绑核 Pthread | 23.3 / 25.3 ms | 14.8 / 14.8 ms |
| 不绑核 OpenMP | 22.8 / 24.5 ms | 14.5 / 14.5 ms |
| P 核 Pthread | 19.1 / 19.1 ms | 9.1 / 9.1 ms |
| P 核 OpenMP | 19.0 / 19.0 ms | 9.1 / 9.1 ms |

- `gcc-11` 11.4.0 与 `g++` 11.4.0 加 pragma 后 P 核也在 9.1–9.4 ms，编译器间稳定。
- 该结果与历史 `-O3 -march=native` 的 8.6–9.1 ms 基本持平（pragma 只开 4 宽 SSE2，未用 AVX2/FMA）。

### 7.3 正确性

- 与标量 plain `-O2` 输出**逐字节相同**（0 字节差异）。
- 教师验卷 PASS，MSE 0.00，相似度 100.00%。
- 与历史 `-O3` 参考图仍只有 29 字节 ±1 舍入差异，相似度 100.00%。

### 7.4 是否采用

- 编译命令仍是 `gcc -O2`，pragma 在源码里，属于源码级优化；作业本身也要求“创新和优化部分”。
- 但 `#pragma GCC optimize` 可能被部分老师视为“绕过 plain O2”的编译器开关。若老师明确要求
  “不许任何额外向量化/优化开关”，则不要用。
- 建议先向老师确认口径；若允许，只需在 `conv_pthread.c` / `conv_omp.c` 顶部各加这一行，
  Makefile 不用改。当前主代码**未加**，以严格保守口径提交。
